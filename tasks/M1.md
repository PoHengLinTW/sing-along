# M1 — Core Player

**Goal:** A working multitrack player built from **uploaded** files: project and track CRUD, synced playback, waveforms, mixer, transport and labels. It runs locally against Postgres and RustFS.

**Exit criteria:** Locally, a user can create a project, upload several tracks with labels, play them in sync, mix them, loop a section and seek using the waveform. Deletes ask for confirmation.

---

### M1-01 Monorepo scaffold + CI
**Depends on:** M0-08
**Scope:** pnpm workspaces with `apps/web` (React + Vite + TS), `apps/api` (Fastify + TS) and `packages/shared`. Add ESLint, Prettier, TS project references, Vitest everywhere, and a GitHub Actions workflow.

**AC:**
- [ ] `pnpm dev` starts the web and api apps together. The web app proxies `/api` to the api in dev.
- [ ] `pnpm lint`, `pnpm typecheck` and `pnpm test` pass from the root.
- [ ] A type exported from `packages/shared` is imported by both apps.
- [ ] A GitHub Actions workflow runs lint, typecheck and test on every push and PR, and it passes.
- [ ] The README has setup instructions (Node version, pnpm, `pnpm dev`).

### M1-02 Local infra: Postgres + S3 stand-in (RustFS) + Drizzle
**Depends on:** M1-01
**Scope:** `docker-compose.dev.yml` with Postgres and RustFS (the local R2 stand-in; MinIO is no longer available as a public image). Drizzle ORM with migrations. Config loaded from the environment and validated with zod.

**AC:**
- [ ] `docker compose -f docker-compose.dev.yml up` starts Postgres and the S3 stand-in. A bucket is created automatically.
- [ ] `pnpm db:migrate` and `pnpm db:generate` scripts work.
- [ ] The API refuses to start, with a clear message, if a required env var is missing or invalid.
- [ ] `.env.example` lists every variable (DB URL, S3 endpoint, bucket, keys, public origin).

### M1-03 Database schema and label seed
**Depends on:** M1-02
**Scope:** Tables `projects`, `tracks`, `labels`, `track_labels`. Tracks have `status` (`pending` | `active`) for the upload-confirm flow. Seed the preset labels.

**AC:**
- [ ] Every field listed in PRD T2 exists on `tracks`, plus `status`. `peaks` is JSONB.
- [ ] `projects` has `title` (not null), `artist`, `notes`, `created_at`, `updated_at`.
- [ ] `labels` has a unique `name`, a `color` and an `is_preset` flag. The 12 presets from PRD L2 are seeded **idempotently** (running the seed twice creates no duplicates).
- [ ] Deleting a project cascades to its tracks and `track_labels`. Deleting a track cascades to its `track_labels`.
- [ ] The migration runs cleanly on an empty database.

### M1-04 Projects API
**Depends on:** M1-03
**Scope:** `GET /api/projects`, `POST /api/projects`, `GET/PATCH/DELETE /api/projects/:id`, validated with zod schemas from `packages/shared`.

**AC:**
- [ ] The list returns id, title, artist, active track count and `updated_at`, newest first.
- [ ] `GET /:id` returns the project with its active tracks (ordered by `sort_order`) and their labels.
- [ ] `POST`/`PATCH` reject an empty title and a title over 200 characters with 400 and a field-level error.
- [ ] `PATCH` updates `updated_at`. An unknown id returns 404.
- [ ] `DELETE` removes the project **and its storage objects** (via the storage service from M1-05) and returns 204.
- [ ] Unit tests cover each endpoint's success and error paths.

### M1-05 Storage service and presigned upload/confirm flow
**Depends on:** M1-03
**Scope:** An S3-compatible client (works with both R2 and RustFS). Endpoints:
- `POST /api/projects/:id/tracks/upload-url` creates a pending track and returns a presigned PUT.
- `POST /api/tracks/:id/confirm` activates the track.
- `GET /api/tracks/:id/audio-url` returns a presigned GET.

**AC:**
- [ ] The upload-url request takes `{name, performer, labels, mimeType, sizeBytes, durationMs, startOffsetMs, source, peaks}`. It rejects MIME types not in the allowed list (PRD T1) with 415.
- [ ] The presigned PUT is signed with the exact `Content-Type` and `Content-Length`. A PUT with a different size is rejected by storage (checked against RustFS).
- [ ] The object key format is `projects/<projectId>/tracks/<trackId>` plus the file extension.
- [ ] Confirm checks the object with HEAD. If it's missing or the size differs, confirm returns 400 and deletes the object. Otherwise the track becomes `active`.
- [ ] Presigned URLs expire after 15 min (configurable).
- [ ] Unit tests use a mocked storage client.

### M1-06 Tracks and labels API
**Depends on:** M1-05
**Scope:**
- `PATCH /api/tracks/:id` (name, performer, labels, start/latency offsets)
- `DELETE /api/tracks/:id`
- `PUT /api/projects/:id/track-order`
- `GET/POST /api/labels`

**AC:**
- [ ] `PATCH` accepts partial updates. Labels are replaced as a set. Offsets are integers within ±600 000 ms.
- [ ] `DELETE` removes the DB row **and** the storage object, and returns 204. It's idempotent: a second call returns 404, never 500.
- [ ] Track order takes the full list of track ids. It rejects ids from another project or a partial list with 400, and saves `sort_order` in one transaction.
- [ ] `POST /labels` creates a custom label (trimmed, 1–30 characters, compared case-insensitively). Creating an existing name returns the existing label.
- [ ] Every track change updates the parent project's `updated_at`.
- [ ] Unit tests cover the above.

### M1-07 Web app shell
**Depends on:** M1-01
**Scope:** React Router routes (`/`, `/project/:id`), a TanStack Query client, a typed API client built on the shared schemas, the base layout, toast notifications, and a reusable `ConfirmDialog` component.

**AC:**
- [ ] Unknown routes show a 404 page. An unknown project id shows a "Project not found" page with a link home.
- [ ] API errors appear as toasts with the server's message. Network errors show "Can't reach server."
- [ ] `ConfirmDialog` supports a title, a message, a destructive button style and an optional **"type X to confirm"** input that keeps the confirm button disabled until the text matches exactly.
- [ ] `ConfirmDialog` is accessible: focus stays inside the dialog, Esc cancels, and focus returns to the trigger when it closes.

### M1-08 Home page: project list and create
**Depends on:** M1-04, M1-07
**Scope:** The public list of projects and a create-project dialog.

**AC:**
- [ ] The list shows title, artist, track count and a relative "updated" time. Clicking a row opens `/project/:id`.
- [ ] When there are no projects, the page shows an empty state with a "Create your first project" call to action.
- [ ] The create dialog validates the title (required, ≤ 200 characters). On success it goes to the new project.
- [ ] Loading and error states are shown (skeleton rows, and a retry button on error).

### M1-09 Project header: inline edit and delete
**Depends on:** M1-08
**Scope:** Edit the title, artist and notes in place with autosave, and delete the project with a confirmation.

**AC:**
- [ ] Text fields save on blur or Enter (not Enter in notes). A "Saved" indicator appears. Esc undoes the edit.
- [ ] Clearing the title shows a validation error and doesn't save.
- [ ] Delete opens `ConfirmDialog`: "Delete '<title>' and its N tracks? This cannot be undone." The user must **type the project title**.
- [ ] After a delete, the app returns home and the project is gone from the list.

### M1-10 Audio engine and transport store
**Depends on:** M1-01
**Scope:** Port the M0 engine into `apps/web/src/audio/`:
- An `AudioEngine` class that loads buffers, handles play, pause and seek, gives each track a GainNode (volume, mute, solo), schedules tracks by `start_offset_ms + latency_offset_ms`, and handles the A–B loop.
- A Zustand store for transport state (playing, position, duration, loop).

**AC:**
- [ ] A **pure function** (unit tested) calculates, for a given playhead and set of tracks, which tracks start when and at what offset into their buffers. Covered cases: negative offsets, tracks starting after the playhead, and a playhead past a track's end.
- [ ] Solo logic is a unit-tested pure function: if any track is soloed, only soloed tracks are audible; mute always wins.
- [ ] Changing volume, mute or solo during playback takes effect within 50 ms without restarting playback.
- [ ] Changing an offset during playback reschedules the affected track only.
- [ ] Position updates at least 30 times per second for the UI, without re-rendering the whole React tree (subscription through a selector).
- [ ] Project duration = the maximum over all tracks of (offset + duration).
- [ ] The `AudioContext` is created or resumed on the first user gesture.

### M1-11 Upload track flow
**Depends on:** M1-05, M1-06, M1-10
**Scope:** File picker and drag-and-drop on the project page. The client checks the file, decodes it for duration and peaks, and then does upload-url → PUT with progress → confirm.

**AC:**
- [ ] Accepts the PRD T1 formats. Anything else is rejected before upload with "Unsupported format."
- [ ] Before uploading, the client computes `durationMs` and peaks (about 100 peaks per second of audio) with a pure, unit-tested peaks function. The peaks JSON for a 10-min track is ≤ 500 KB.
- [ ] An upload form collects the name (defaults to the file name), performer (pre-filled from localStorage) and labels.
- [ ] Progress is shown as a percentage. Cancelling aborts the PUT, and the pending track is left for cleanup.
- [ ] On success the new track appears in the view without a page reload (the query is invalidated).
- [ ] Several files dropped at once upload one after another, each with its own form or defaults.

### M1-12 Multitrack waveform view
**Depends on:** M1-10, M1-11
**Scope:** Render each track's waveform from its stored peaks (wavesurfer.js, per the M0-07 decision), placed at its offset on a shared timeline with a playhead that follows the engine.

**AC:**
- [ ] Waveforms appear before the audio has finished downloading (they come from peaks only). A per-track loading indicator shows until the buffer is ready.
- [ ] A track is shifted horizontally by `start_offset_ms + latency_offset_ms`.
- [ ] The playhead moves smoothly while playing and matches the engine position within 1 frame.
- [ ] Clicking or dragging on the timeline or ruler seeks. Seeking while playing continues playback from the new point.
- [ ] Zoom in and out (buttons and Ctrl/Cmd + scroll) and horizontal scrolling. The view auto-follows the playhead while playing unless the user has scrolled away.
- [ ] A time ruler shows mm:ss marks that adapt to the zoom level.

### M1-13 Track row controls and reordering
**Depends on:** M1-12
**Scope:** A control panel on the left of each track row: name, performer, volume slider, mute, solo, delete. Rows can be dragged to reorder.

**AC:**
- [ ] The volume slider (0–150%, default 100%) changes the gain live, whether playing or stopped.
- [ ] Mute and solo toggle and look clearly active or inactive. They follow the M1-10 solo logic.
- [ ] Name and performer can be edited in place and save on blur (PATCH).
- [ ] Delete opens `ConfirmDialog`: "Delete '<track name>'? This cannot be undone." After confirming, the track is removed from the engine and the view.
- [ ] Dragging rows reorders them and saves through the track-order endpoint. The list rolls back with a toast if the save fails.

### M1-14 Transport bar and keyboard shortcuts
**Depends on:** M1-10
**Scope:** A transport bar with restart, −10 s, play/pause, +10 s and a time display (current / total). Keyboard shortcuts as in PRD §5.5 (record and mic-mute shortcuts come in M2).

**AC:**
- [ ] Restart seeks to 0 and keeps playing if playback was running.
- [ ] −10 s stops at 0. +10 s stops at the end, and reaching the end stops playback.
- [ ] Space, Home, ← and → work, but **not** while focus is in a text input, textarea or contenteditable.
- [ ] The time display shows `mm:ss.s / mm:ss`.
- [ ] Buttons have tooltips that show their shortcut, and aria-labels.

### M1-15 A–B loop
**Depends on:** M1-12, M1-14
**Scope:** Define a loop region by dragging on the ruler, or with "Set A" and "Set B" buttons at the playhead. Toggle looping and clear the loop.

**AC:**
- [ ] Dragging on the ruler creates a highlighted region. Its edges can be dragged to adjust it.
- [ ] With looping on, reaching B jumps back to A with a gap of ≤ 50 ms and no stuck notes or buffer glitches.
- [ ] Seeking outside the loop while looping is on: playback continues to B only if the playhead is before B. Otherwise the loop is ignored until the playhead re-enters it.
- [ ] B must be after A (at least 0.5 s apart). Clearing removes the region.
- [ ] Unit tests cover the loop boundary logic.

### M1-16 Labels UI
**Depends on:** M1-06, M1-13
**Scope:** Label chips on each track, a label picker (presets + create custom), a track color taken from its first label, a label filter, and bulk mute or unmute by label.

**AC:**
- [ ] The picker lists presets and existing custom labels with type-ahead. Typing a new name offers "Create '<name>'."
- [ ] Chips use the label color. The waveform color comes from the first label (a neutral color if the track has none).
- [ ] The label filter hides tracks that don't have the chosen labels. Hidden tracks **keep playing** according to their mute state.
- [ ] "Mute all <label>" and "Unmute all <label>" toggle every matching track.
- [ ] The upload form (M1-11) uses the same picker.

### M1-17 Mixer persistence per browser
**Depends on:** M1-13
**Scope:** Save each track's volume, mute and solo, plus the zoom level, to localStorage, keyed by project id.

**AC:**
- [ ] Reloading the page restores volume, mute, solo and zoom for that project.
- [ ] Mixer state for deleted tracks is ignored and removed. New tracks default to 100%, not muted, not soloed.
- [ ] Mixer state is **never** sent to the server. Two browsers can hold different mixes of the same project.
- [ ] A "Reset mix" action restores the defaults.
