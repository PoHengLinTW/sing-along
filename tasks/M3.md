# M3 — Hardening and Deploy

**Goal:** Enforce the storage caps, clean up orphaned uploads, polish error handling, and deploy to the homelab behind Cloudflare Tunnel with R2.

**Exit criteria:** The app runs at `https://<your-domain>` against real R2, the caps are enforced, and the Playwright smoke flows pass in CI.

---

### M3-01 Caps configuration and server enforcement
**Depends on:** M1-05
**Scope:** Enforce every PRD §5.9 cap on the server, with limits set through env vars (defaults as in the PRD).

**AC:**
- [ ] upload-url rejects:
  - `sizeBytes > 60 MB` → 413
  - `durationMs > 10 min` → 422
  - a project that already has 10 tracks (active + pending) → 409
  - a global total (active + pending `size_bytes`) + new file > 8 GB → 507
- [ ] `POST /projects` rejects a new project once 100 exist → 409.
- [ ] Every rejection returns a machine-readable `code` (e.g. `TRACK_LIMIT`, `STORAGE_FULL`) and a human-readable message.
- [ ] Checks and inserts run in a transaction (or under an advisory lock), so two uploads at the same moment can't both push past a cap.
- [ ] Unit tests cover each cap at, just under, and just over the limit.

### M3-02 Storage usage endpoint and home-page indicator
**Depends on:** M3-01, M1-08
**Scope:** `GET /api/storage` returns bytes used and the limit, plus the project count and limit. The home page shows the storage used.

**AC:**
- [ ] The endpoint returns `{usedBytes, limitBytes, projectCount, projectLimit}`. `usedBytes` counts active tracks only.
- [ ] The home page shows e.g. "5.2 / 8 GB used" with a bar that turns amber at 80% and red at 95%.
- [ ] The indicator refreshes after uploads and deletes.

### M3-03 Cap-aware UX
**Depends on:** M3-01
**Scope:** Show the caps in the UI before users run into them, and turn server rejections into clear messages.

**AC:**
- [ ] Oversized files (> 60 MB) and files over 10 min are rejected **on the client** before uploading, with messages naming the limit. WAV files get the hint "convert to FLAC or MP3."
- [ ] At 10 tracks (drafts don't count), the upload button is disabled with a tooltip "Track limit reached (10)." Recording is still allowed, but uploading the draft shows the limit message.
- [ ] A `STORAGE_FULL` rejection shows "Storage full (8 GB) — delete old tracks or projects."
- [ ] At 100 projects, "Create project" is disabled with an explanation.

### M3-04 Orphan and pending cleanup job
**Depends on:** M1-05
**Scope:** A nightly job, run in the API process with a scheduler such as `node-cron` or croner, that deletes stale pending tracks and orphaned storage objects.

**AC:**
- [ ] It deletes `pending` tracks older than 24 h, along with their storage objects if present.
- [ ] It lists the bucket's objects under `projects/` and deletes any with no matching DB row that are older than 24 h.
- [ ] A `--dry-run` CLI command (`pnpm cleanup --dry-run`) logs what would be deleted without deleting anything.
- [ ] Each run logs counts (pending removed, orphans removed, bytes freed).
- [ ] Unit tests use a mocked storage client and a test DB.

### M3-05 Error, loading and empty-state pass
**Depends on:** M2-09
**Scope:** Check the flows touched in M1 and M2 for consistent loading states, error recovery and empty states.

**AC:**
- [ ] Every data fetch has a loading state and an error state with a retry button. No blank screens.
- [ ] When an audio download fails, the track shows "Failed to load audio — Retry" and the rest of the project still plays.
- [ ] An expired presigned GET URL is refreshed and retried automatically once.
- [ ] A project with no tracks shows an empty state with "Upload a track" and "Record" actions.
- [ ] The API has a global error handler that logs details on the server and returns a generic 500 message to the client (no stack traces).

### M3-06 Production Docker image
**Depends on:** M1-01
**Scope:** A multi-stage Dockerfile that builds the web and api apps. Fastify serves the API under `/api` and the built web assets with SPA fallback.

**AC:**
- [ ] `docker build` produces a single image under 300 MB that runs as a non-root user.
- [ ] `/api/*` goes to the API. Other paths serve static files, and unknown paths fall back to `index.html`.
- [ ] Static assets with a hash in their name get `Cache-Control: immutable, max-age=31536000`. `index.html` and the service worker get `no-cache`.
- [ ] Database migrations run automatically on container start, before the server starts listening.
- [ ] `GET /api/health` returns 200 when the DB is reachable and 503 otherwise.

### M3-07 Production Compose stack with Cloudflare Tunnel
**Depends on:** M3-06
**Scope:** `docker-compose.yml` with app, postgres (on a named volume) and cloudflared, configured through `.env`.

**AC:**
- [ ] `docker compose up -d` brings up all three. The app waits for Postgres to be healthy.
- [ ] Postgres data survives `docker compose down && up`.
- [ ] cloudflared routes `https://<domain>` to the app container. No host ports are exposed except (optionally) a localhost-only port for debugging.
- [ ] The README deploy section covers the tunnel token, env vars, first start and updating to a new image.

### M3-08 R2 bucket setup and CORS
**Depends on:** —
**Scope:** Create and configure the R2 bucket, scoped credentials and CORS, and document the steps.

**AC:**
- [ ] The R2 bucket exists, with an API token limited to **that bucket** (Object Read & Write).
- [ ] The CORS policy allows `PUT` and `GET` (and `HEAD`) from the app origin with headers `Content-Type` and `Content-Length`. Other origins are rejected (checked with curl or the browser).
- [ ] A Cloudflare billing or usage notification is set up.
- [ ] The README has step-by-step R2 setup instructions, and the payment-method requirement is noted.

### M3-09 Deploy and production smoke test 📱
**Depends on:** M3-07, M3-08, M3-01 … M3-05
**Scope:** The first real deployment, with a manual smoke test against real R2.

**AC:**
- [ ] The app loads over HTTPS at the production domain on desktop and iPhone.
- [ ] Create project → upload track → record and upload take → play in sync → delete track → delete project all work against R2. The bucket is empty afterwards (no leftover objects).
- [ ] The mic permission prompt works on the production origin.
- [ ] The storage indicator shows the correct figure.

### M3-10 Playwright smoke e2e in CI
**Depends on:** M3-06
**Scope:** A few critical-flow e2e tests that run in CI against the Compose stack with RustFS.

**AC:**
- [ ] Flow 1: create project → upload a small audio fixture with a label → the track appears with its waveform → play → the time display advances.
- [ ] Flow 2: delete track (confirm) → delete project (type the title) → the project is gone from the home page.
- [ ] Flow 3: the upload is rejected when the project already has 10 tracks (seeded), and the limit message is shown.
- [ ] The tests run in GitHub Actions (Chromium, fake media flags) and pass reliably across 3 consecutive runs.
