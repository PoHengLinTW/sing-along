# M0 — Spike: Prove the Audio Core Works (throwaway)

**Goal:** Before building any product code, find out whether in-browser synced playback, recording at the playhead, lossless encoding and manual latency alignment work well enough on the devices we care about.

**Location:** `spike/` (Vite + vanilla TypeScript, no framework). The code is thrown away afterwards. What carries forward is the knowledge in `spike/SPIKE_NOTES.md` plus audio-engine code that M1 ports deliberately.

**Exit criteria:** `SPIKE_NOTES.md` contains a go/no-go for the recording approach, the chosen FLAC encoder, the wavesurfer usage decision, and measured latency and memory figures per device.

---

**AC:**

### M0-02 Synced playback of 3 local files
**Depends on:** M0-01
**Scope:** Load 3 audio files through a file input, decode them to `AudioBuffer`s, and play them in sync with `AudioBufferSourceNode`s scheduled at the same `AudioContext` time. Add play, pause, seek and a volume control per track.

**AC:**
- [x] All three tracks start together (scheduled at the same `ctx.currentTime + ε`).
- [ ] Pause at time *t* and resume: every track continues from *t*. No audible flam between tracks. _(open: manual: needs listening for flams)_
- [ ] Seeking to any time via a range input restarts every track at that position. _(open: code done, not exercised in a browser)_
- [ ] Changing a track's volume while it plays takes effect immediately (GainNode), with no clicks. _(open: code done (10 ms gain smoothing); needs listening)_
- [ ] After 5 minutes of continuous playback there's no audible drift between tracks. _(open: not measured; only a 30 s probe was run)_
- [ ] Works with mp3, m4a, wav and flac inputs (compatibility gaps noted per browser). _(headless Chromium, Firefox and WebKit decoded all four via the file input; real Chrome/Safari playback still open)_

### M0-03 AudioWorklet mono capture at the playhead 📱
**Depends on:** M0-02
**Scope:** Capture mic input through an AudioWorklet as Float32 mono while the tracks play, starting at the current playhead. Record the take's start offset.

**AC:**
- [ ] `getUserMedia` is called with `echoCancellation`, `noiseSuppression` and `autoGainControl` = `false` and `channelCount: 1`. `track.getSettings()` confirms this (the actual values are logged per browser in the notes). _(real Chrome 153 reports all false and 1 channel; desktop Safari and iPhone pending)_
- [x] Pressing Record at playhead *t* stores `startOffsetMs ≈ t`, computed from `AudioContext` time, not `Date.now()`. _(headless fake mic at 5.000 s stored 4.941 s from first-frame AudioContext time; the 59 ms lead is before scheduled playback)_
- [x] A 60-second take's sample count matches 60 s × sampleRate within ±50 ms. _(headless fake mic at a nonzero playhead captured 60.018 s at 44.1 kHz; real-device checks remain under the next criterion)_
- [ ] Works on desktop Chrome, desktop Safari and iPhone Safari. The sample rate for each is recorded in the notes. _(open: manual: device matrix is blank)_

### M0-04 Evaluate and choose a FLAC encoder (+ WAV fallback) 📱
**Depends on:** M0-03
**Scope:** Encode the captured take to FLAC (16-bit mono) in a Web Worker using a WASM encoder, and produce a WAV version as the fallback. Compare at least 2 encoder candidates (e.g. libflac.js and one alternative).

**AC:**
- [ ] A 1-minute take encodes to FLAC 16-bit mono. The file is roughly 3–3.5 MB per minute for voice. _(real Chrome 23.3 s voice take encoded to 0.70 MB, 1.80 MB/min; full-minute take and size-estimate review pending)_
- [ ] The FLAC output decodes with `decodeAudioData` in Chrome, Safari and Firefox, and sounds the same as the source. _(open: decodes in headless Chromium/Firefox/WebKit; real Safari and listening pending)_
- [ ] Encoding a 4-minute take takes under 10 s on the iPhone. The actual time is recorded. _(open: manual: only 0.7 s measured in Node, iPhone not run)_
- [ ] The WAV 16-bit mono fallback plays in all three browsers. _(open: decodes in headless engines; playback not checked)_
- [x] The notes record, for each candidate: license, WASM/bundle size, encoding speed, maintenance status, **chosen encoder and why**. _(libflacjs asm.js and independent Mediabunny WASM compared on the same four-minute input in headless Chromium, Firefox and WebKit; iPhone choice remains provisional)_

### M0-05 Take playback with manual latency slider 📱
**Depends on:** M0-03
**Scope:** Play the recorded take together with the other tracks at `startOffset + latencyOffset`, with a ±500 ms slider to line it up by ear. Measure typical latency.

**AC:**
- [ ] The take plays in sync with the mix, starting at its recorded offset. _(open: code done; not heard, no real take)_
- [ ] Moving the latency slider (1 ms steps, arrow keys work) audibly shifts the take. The new value applies on the next play or seek. _(open: slider and clamp done; audible shift not heard)_
- [ ] A clap-along test is done on each device with **wired headphones** and with **Bluetooth**. The offset that lines up is recorded in the notes, along with the browser-reported `outputLatency + baseLatency`, for comparison with the future automatic detection. _(open: manual: wired and Bluetooth clap-along not done)_

### M0-06 Crash-safe chunk persistence in IndexedDB 📱
**Depends on:** M0-03
**Scope:** Write captured PCM chunks to IndexedDB about once a second during recording. On reload, rebuild any unfinished take.

**AC:**
- [x] Reload or kill the tab 30 s into a recording. After reopening, a recovered take of ≥ 28 s is offered and plays correctly. _(headless Chromium offered 30.0 s; user confirmed the real desktop Chrome recovery passed and the take played)_
- [ ] Writing chunks causes no audible glitches in playback or the take (checked on the iPhone). _(open: manual: needs iPhone)_
- [ ] The notes record the storage quota reported by `navigator.storage.estimate()` on each device. _(desktop Chrome 153: 10.74–10.75 GB; desktop Safari and iPhone pending)_

### M0-07 wavesurfer.js multitrack evaluation
**Depends on:** M0-02
**Scope:** Decide how wavesurfer.js v7 fits in. Either (a) the multitrack plugin handles playback too, or (b) wavesurfer only renders waveforms from precomputed peaks while our Web Audio engine handles playback.

**AC:**
- [x] Both approaches are prototyped with the 3 test files.
- [x] Measured: drift between tracks after 5 min of playback for (a), and playhead sync accuracy for (b). _(headless Chromium 145: multitrack inter-track spread 168.3 ms at 5 min; rendered playhead within 11.7 ms of the AudioContext timeline; real-device listening still open)_
- [x] Rendering from **precomputed peaks** (no audio decode) works, and positioning a track by start offset works.
- [x] A decision is recorded in the notes. Default expectation: (b).
